## 先约定一个可验收的试点

接入条件尚不明确时，建议先用一次小范围 POC 验证；是否需要 POC，由双方按项目情况确认。有明确范围的企业项目也可以直接评估。需要试点时，选择有明确负责人的真实工作，写清输入、期望产物、允许访问的系统和完成标准。例如，在一个已授权的代码仓库中实现限定功能，交付代码变更、检查结果与说明，再由仓库负责人验收。

首次评估不必同时开放全部仓库、知识空间和写权限。先列出本次确实需要的资源；对于合并代码、修改外部记录等操作，分别说明是否纳入范围、由谁授权。POC 的结果应能回答“是否完成约定工作”，而不只是“能否生成一段回复”。

## 确认参与者与资源归属

平台管理员或运维角色负责模型服务、运行环境和企业连接的配置；工作区管理员维护本工作区的成员和策略；参与工作的成员使用自己的授权完成操作。能管理平台配置，不代表自动拥有所有工作区内容的读取权。

接入前整理以下材料，并指定维护人：

| 材料 | 需要确认的内容 |
| --- | --- |
| 试点工作 | 目标、输入、交付物、验收人及不包含的操作 |
| 身份与工作区 | 参与账号、角色、资料归属和访问范围 |
| 模型与企业工具 | 实际服务地址、可用模型、接口协议及授权方式 |
| 执行环境 | 集群、存储、网络出口、镜像获取方式及运维负责人 |
| 知识来源 | 允许使用的文档、原文访问权限、更新与失效处理方式 |

## 核对真实的数据流

私有部署不直接意味着数据不离开企业环境。代码、文档、工具参数和模型输入可能沿不同路径传递，应分别核对模型网关、代码托管、知识检索、企业连接器和遥测的目标地址。外部模型或第三方工具是否允许接收这些内容，需要按本次企业要求确认。

共享一个工具或知识库，也不等于共享个人凭据。应使用正式授权入口保存或轮换密钥，不把密钥写进任务说明、共享文档或演示截图。访问被撤销之后，再检查后续请求是否按当前权限被拒绝；撤销不能回滚已经发生的外部操作。

## 分开验证环境和业务

建议按以下顺序收集证据：

1. 使用真实身份登录，确认所属工作区与角色。
2. 完成一次实际模型调用，核对模型及使用的授权。
3. 创建执行环境并操作文件，检查停止、重启后的数据保留。
4. 导入允许使用的文档，完成索引、检索和原文追溯。
5. 执行约定工作，审查代码、文件、工具结果和检查记录。
6. 由验收人记录接受、需返工或暂不纳入范围的结论。

服务健康、运行结束、自动检查通过、人工接受、代码合并和生产发布是不同结果，应分别记录。官网中的工作台示例只能帮助理解交互，不能替代上述企业环境验收。

## 试点之后如何扩大使用

整理一份试点记录：实际版本、环境、工作范围、交付物、失败原因、人工处理步骤与未完成事项。扩大到更多成员、仓库或长期运行前，补充目标环境所需的容量、备份恢复、身份接入和维护窗口验证。

当前产品已有可运行的本地验证切片；具体生产可用性、服务保障及高可用方案仍需按交付范围确认。下一步可阅读[技术架构](/docs/architecture)、[部署入口](/docs/deployment)，或[联系团队规划 POC](/poc)。
