## 先固定出问题的环境

记录产品版本、集群 context、namespace、发生时间，以及受影响的工作或运行入口。先判断问题发生在安装、环境创建、模型调用、知识处理还是交付阶段，避免把所有失败都当作模型问题。

下面命令使用本地示例安装点。前三条只读取状态；健康检查还要求已有端口转发或实际配置的访问入口。它们不会替您重启或修复服务。

```bash
helm --kube-context minikube-ubuntu -n fusion status fusion
kubectl --context minikube-ubuntu -n fusion get deploy,pod,svc,pvc,job
kubectl --context minikube-ubuntu get crd sandboxes.agents.x-k8s.io
curl --fail http://localhost:8080/readyz
```

## 预检失败或 Sandbox 无法创建

若提示无法访问集群，先核对 kubeconfig 中的目标 context 和当前身份权限；若找不到 Sandbox CRD，按随附前置手册检查 Controller 安装。CRD 存在仍需检查 Controller 与实际 Sandbox Pod，不能据此宣布运行时可用。

当前本地 `default` 使用节点普通 OCI 运行时。需要 gVisor 时，节点必须有实际可运行的 handler，并通过对应探针；创建同名 RuntimeClass 不会安装运行时。网络策略对象同样需要网络层真正执行。

Controller 安装、运行探针和任何重启都会改变集群，应在确认操作范围后执行；不要为了绕过预检临时关闭相关校验。

## 镜像拉取失败或启动超时

遇到 `ImagePullBackOff`，依次核对节点架构、配置的镜像引用、节点到镜像仓库的连通性，以及安装 namespace 内的拉取 Secret。本机 Docker 已登录或已有同名镜像，不代表 Kubernetes 节点具备拉取能力。

若组件等待模型下载，继续核对下载网络与 Pod 事件。不要只增加超时掩盖无法拉取、凭据无效或架构不匹配。使用经验证的发布 digest，避免用一个可变标签替换原来固定的版本。

## PVC 未绑定或重启后看不到文件

先检查 PVC 状态、StorageClass 和原卷身份，再核对实际挂载路径。`Pending` 与卷已绑定但内容不符是不同问题；恢复后的同名 PVC 也不一定是原来的数据。

不要新建空卷替代缺失卷，也不要删除原 PVC 来让 Pod 启动。已有安装先保留配置、Secret 和备份，按随附迁移手册恢复。单节点存储测试不能证明跨节点或集群重建后仍会保留数据。

## Console 可用，但模型或知识失败

健康接口通过只说明相应服务状态。模型失败时检查实际网关地址、启用模型、支持协议、当前调用使用的凭据及额度。保存目录不等于调用已经验证，可用一次明确的小请求复现。

知识问题另行检查 LightRAG 是否启用、真实组织 ID 是否正确、组织运行环境及 Embedding 是否可用，再检查文档索引与原文授权。不要关闭 LightRAG 把临时 bootstrap 当成完整安装；也不要用随机组织 ID 代替初始化。

## 页面、预览或授权回跳异常

端口转发能访问但 Cookie、iframe 或预览异常时，核对浏览器实际来源与 `publicURL`，再检查域名路由和证书。已有 HTTPS 安装应保留正确地址与可信证书链，不以跳过 TLS 校验作为修复方式。

升级后只有旧任务或开发机异常时，核对它们的实际 Runtime 镜像及持久化配置。Helm 更新不会自动替换所有既有运行环境，控制面和 Runner 也需要使用兼容版本。

## 如何提交一份有用的问题记录

保留复现步骤、预期与实际结果、时间范围、版本、脱敏状态信息和相关工作入口。记录失败前后的操作，区分“停止请求已接受”“进程已退出”和“业务完成”。结果未知的外部写操作先核对回执，避免盲目重复。

交接材料中移除密钥、Token、个人资料和私有文档正文。需要协助时，[联系团队](/poc)并提供上述范围；安装流程见[部署指南](/docs/deployment)。
