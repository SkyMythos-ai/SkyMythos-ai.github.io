---
title: Turn work experience into employee capabilities
description: Understand responsibilities, skills, knowledge, and improvement proposals that require review.
---

Digital employees have reusable definitions and configuration. Actual collaboration also depends on the current member's authorization, the employee's state, and the work context. This guide follows the current creation page and distinguishes generating a proposal, saving a definition, and actually completing work.

## Start in the employee directory [#start-in-the-employee-directory]

Choose "Create employee" in the directory to open the dedicated creation page. It offers "Define directly" and "Learn from work experience". Direct definition suits an established responsibility; learning from experience suits reusable experience that can help draft instructions.

An employee's directory visibility differs from the employees a person already uses. Finding a shared definition does not grant access to the external systems it depends on.

## Define an employee directly [#define-an-employee-directly]

Enter basic information first, then describe how the employee should work:

| Field | Purpose |
| --- | --- |
| Name | Help the team recognize the responsibility, for example "Feedback analysis assistant" |
| Visibility | Set where the definition is visible; choices depend on management permissions |
| Introduction | Optionally describe suitable tasks in one sentence for discovery in the directory |
| Prompt | Define the inputs, steps, outputs, and circumstances that require confirmation |
| Model | Select an available model; execution adapts to that choice |
| Additional capabilities | Associate capabilities as needed; selection does not replace actual authorization |

A name, prompt, and available model are required before submission. If an available default model is already selected, you do not need to select it again. If no model is available, submission displays a field error; an enabled button alone does not prove all prerequisites are satisfied. Public visibility requires the corresponding management permissions. Begin with the knowledge and tools needed for the responsibility rather than adding everything.

After choosing "Create employee", check the saved result and details. The current interface applies the definition when saved; there is no universal extra "Publish employee" step. Actual execution still depends on prerequisites and authorization.

## Draft an employee from experience [#draft-an-employee-from-experience]

1. Switch to "Learn from work experience" and enter the responsibility you want to define.
2. Select available experience sources and inspect their title, associated employee, version, content, and scope. Sources that cannot be reused, are unverified, excluded, or have changed versions explain their status.
3. Choose "Analyze selected experience", then inspect the analysis state and returned proposal. Analysis requires a goal and at least one valid source; opening the page alone does not start it.
4. Review the proposed name, responsibility, and sources. Choose "Use proposal and edit employee" to return to the full form for further changes.
5. Complete the model, capabilities, and visibility, then explicitly create the employee.

"Use proposal" updates only the current draft; it does not automatically hire an employee or start work. If the form already has content, replacing its name, introduction, and instructions requires confirmation. The model, avatar, capabilities, and visibility are retained.

## Improve an existing employee [#improve-an-existing-employee]

Training an existing employee differs from drafting a new one. "Train employee definition" selects experience for a specific employee, collects a training goal, and presents a proposal for review. Saving the training result starts only after explicit confirmation. The current confirmation says "Confirm training and save results"; do not follow outdated instructions that universally require another publication step.

Check whether the operation finished, the result was actually saved, and the target employee's configuration is correct. Existing work retains its starting configuration snapshot. Saving a new configuration does not mean work already running immediately adopted it.

## Check a real collaboration [#check-a-real-collaboration]

Employee details expose work records, memory, and recall information. Employees in an eligible state can start collaboration. This opens SkyBot with the employee context, and the visitor still needs to provide a work goal. Source conversations and experience entries should correspond. Another person's historical records must not be treated as a new employee's own experience.

For a POC, test the method on another piece of work with similar scope and record a person's acceptance conclusion. Saving configuration does not automatically prove a training effect, and this process does not modify the underlying model's parameters.

## Common issues [#common-issues]

- **The model list is empty:** Ask an administrator to check available models. Retry a failed read while keeping form content.
- **Experience cannot be selected or a proposal cannot be used:** Read the source status, select again, and analyze. Do not bypass source checks.
- **Training is rejected or configuration conflicts:** Check the employee state, permissions, and latest definition before restarting from the current page. Do not create duplicate employees as a substitute.
