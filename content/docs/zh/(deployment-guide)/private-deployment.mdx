当企业决定评估或正式引入 SkyMythos 时，建议通过范围清晰、可量化核验的小型试点（POC）完成端到端检查；对于需求边界已经十分明确的企业项目，也可以直接进入交付评估。需要规划评估环境时，欢迎先[联系团队预约 POC](/zh/poc)。

## 规划一个可验收的试点范围 [#agree-on-a-pilot-with-acceptance-criteria]

一个成功的 POC 应当能够明确回答“是否按团队标准完成了约定工作”，而不仅仅是“模型能否回复一段文字”。在启动前建议敲定四项范围原则：

1. **指定真实负责人**：每项试点工作都要有明确的业务或研发验收人。
2. **明确输入、产物与排除项**：例如“在一个测试代码仓库中完成限定功能改动，交付代码 Diff、单测检查记录与说明文档；不自动合并保护分支、不修改生产环境”。
3. **坚持最小必要授权**：首次试点不必同时开放全部代码库、所有知识空间或外部系统写权限；先列出本次工作真正需要的资源列表。
4. **事前约定动作审批**：对于代码合并、对外发送消息、变更生产配置等高影响动作，事先写明由谁以何种方式拍板。

## 整理接入清单与分工矩阵 [#identify-participants-and-resource-ownership]

接入准备阶段建议由企业侧明确以下五类材料的维护人（注意：能维护平台基础设施配置，不自动等价于可以查阅各个业务工作空间的私有内容）：

| 准备材料 | 需要提前明确的核心信息 | 建议负责角色 |
| --- | --- | --- |
| 试点工作清单 | 1–2 个具体目标任务、输入样本、期望交付物、验收人及明确不做的动作 | 业务或研发负责人 |
| 身份与工作空间 | 参与人员账号、企业 SSO 对接方式、角色划分及各成员可访问范围 | 组织 Admin / IT |
| 模型与企业工具 | 实际 LLM / Embedding 网关地址、可用模型协议、Git 托管与工具授权策略 | 平台运维 / 架构师 |
| 执行环境条件 | Kubernetes 集群版本、StorageClass 持久化存储、网络出口策略与镜像获取方式 | 基础设施 / 运维团队 |
| 知识来源边界 | 拟导入试点测试的文档范围、原文访问权、更新频率与失效处理方式 | 知识管理员 |

## 核对真实的全链路数据流向 [#check-actual-data-flows]

<Callout type="warn" title="“私有化部署”不自动等于“零外部数据发送”">
  控制面与沙箱部署在企业自身集群内，但代码片段、知识正文、工具参数与模型提示词仍可能沿不同网络路径传输。上线前务必按下列路径逐项核对出站目标地址是否符合企业安全合规要求。
</Callout>

- **模型推理链路**：确认 LLM Gateway 与 Embedding Gateway 指向的是企业内网私有模型服务，还是经合规审批的外部云端 API 端点。
- **代码与外部连接器**：核对 Git 托管仓库地址、企业 IM（飞书 / Lark / Slack）及所接入 MCP 工具服务器的网络出口与允许访问的最小范围。
- **遥测与大对象存储**：核对 PostgreSQL、对象存储（S3 兼容存储）及 OpenTelemetry / GreptimeDB 链路日志的落盘位置与访问权限。
- **凭据隔离与撤销验证**：确认成员个人凭据均通过受控入口保存；在试点期间可专门测试一次“撤销某成员连接授权”，验证后续新请求是否立即被拒绝。

## 六步标准化 POC 验收取证流程 [#verify-the-environment-and-business-outcome-separately]

建议按以下六个顺序逐项执行并保留截屏或日志证据（官网中的本地演示场景仅用于说明交互逻辑，不能替代真实环境验收）：

<Steps>
  <Step>
    ### 1. 真实身份登录与权限核验

    使用真实成员账号（本地或企业 SSO）登录 Console，核对其所属 Workspace 与角色视图是否正确隔离。
  </Step>
  <Step>
    ### 2. 实际模型调用连通验证

    通过当前身份完成一次 LLM 与 Embedding 实际请求调用，核对返回模型 ID 与耗用凭据归属。
  </Step>
  <Step>
    ### 3. 开发机文件操作与持久化验证

    启动个人开发机并在 `/workspace` 写入测试文件，执行停止并重新启动（或重建 Pod），确认文件与数据完整保留。
  </Step>
  <Step>
    ### 4. 知识库索引与原文溯源验证

    导入一份测试文档并发布版本，待索引变为“可检索”后执行检索测试，确认能够点击结果打开同一版本原文核对上下文。
  </Step>
  <Step>
    ### 5. 约定试点任务端到端执行

    执行事先选定的研发 Task（包含已发布 Skill 与 Unit Gate）或业务分析任务，审查完整变更、产物、工具记录与遥测链路。
  </Step>
  <Step>
    ### 6. 业务责任人出具验收结论

    由验收负责人分别记录“环境就绪”“自动检查通过”“人工业务接受”三项结论，明确需返工项或暂不纳入范围的边界。
  </Step>
</Steps>

## 从试点迈向正式规模化推广 [#expand-after-the-pilot]

完成小范围试点后，建议沉淀一份包含**实际使用版本、部署拓扑、交付物清单、遇到的问题与人工干预步骤**的试点总结报告。在扩大到更多部门、更大并发或长期生产运行前，需补充目标环境的容量压测、备份与灾备恢复演练、升级维护窗口验证以及企业高可用方案确认。

当前产品已具备可运行的本地与云原生验证切片；具体生产交付边界与服务保障范围以项目交付合同为准。下一步可继续阅读[技术架构与安全边界](/zh/docs/architecture)、[Kubernetes 私有化部署与升级](/zh/docs/deployment)，或[联系团队规划 POC](/zh/poc)。
