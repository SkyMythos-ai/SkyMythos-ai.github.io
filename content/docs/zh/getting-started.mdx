title: 从一次有验收标准的工作开始
description: 准备目标、上下文和授权，完成一次小范围试点。
---

这份指南面向已经获得工作区访问权限的成员。尚未接入的企业，可先[申请 POC](/zh/poc)，与团队约定评估环境和范围；官网中的产品场景不会替你创建真实任务。

## 先准备一项能判断对错的工作 [#choose-work-with-a-checkable-outcome]

第一次使用，建议选择资料来源明确、结果容易检查的小目标。例如，整理一组客户反馈，形成带来源的改进建议；或为测试仓库补充一个明确的校验。这是 POC 方法建议，系统不会自动替你判断企业的成功标准。

发送前写清四件事：需要解决什么、允许使用哪些资料、希望交付什么、哪些动作必须由人决定。可以参考以下输入，按实际工作修改：

```text
目标：整理本次提供的客户反馈，提出三项优先改进建议。
资料：仅使用我授权的反馈文档与产品接入说明。
交付：每项建议说明问题、来源与建议的验收方式。
边界：先形成建议，不修改生产配置，不对外发送消息。
```

不要在目标中粘贴 API Key 或他人的凭据。连接和授权应通过产品提供的配置入口准备，而不是靠一句“可以访问全部系统”获得权限。

## 按工作类型选择入口 [#choose-an-entry-point-by-work-type]

| 你的目标 | 适合的入口 | 首次检查重点 |
| --- | --- | --- |
| 围绕长期目标补充资料、讨论和分工 | [项目工作](/zh/docs/projects) | 项目名称、上下文、主会话与相关 Thread |
| 基于代码仓库完成有阶段和检查要求的改动 | [研发任务](/zh/docs/tasks) | 需求、Repository、Base branch、Flow 和必填输入 |
| 按重复规则或事件执行固定工作 | [自动化](/zh/docs/automations) | 流程定义、运行环境、触发方式与每次运行结果 |

这些是不同入口，不是一个任务必须依次经过的三个阶段。普通对话中的 Thread 也不会仅因执行了工作，就自动成为研发任务列表中的 Task。

## 准备最小必要的上下文 [#prepare-the-minimum-necessary-context]

进入目标工作区，确认当前成员可用的模型、知识和连接。研发任务需要可读取的代码仓库与基线分支；选择的 Flow 可能还要求额外输入或连接。模型目录可见、个人凭据就绪与实际调用成功，需要分别确认。

知识资料先检查是否已经发布、索引是否可用，以及自己是否有读取权限。具体做法见[企业知识](/zh/docs/knowledge)。为员工选择职责与能力时，见[数字员工](/zh/docs/employees)。共享某项知识或员工定义，不会同时授予其他成员的私人凭据。

## 发起以后看什么 [#what-to-inspect-after-starting]

在对应工作面查看输入是否被接收、当前进度、工具记录和产物。遇到明确的提问或批准请求，先读清对象和操作，再决定如何回应。页面显示“正在运行”或请求已受理，都不等于业务目标已经完成。

第一次评估建议记录：原始目标、所用资料版本、实际输出、检查结果，以及仍需人决定的事项。产品提供执行和产物依据；这些记录怎样纳入企业评估，由团队确定。

## 用产物完成验收 [#accept-the-work-using-its-artifacts]

先核对输出能否打开、是否覆盖原目标，再检查资料引用与相关验证。代码类工作还需查看差异、基线和检查记录。执行结束、自动检查通过、人工接受、代码合并与生产发布是不同事实，不要用其中一个替代其余步骤。

如果发现值得复用的方法，先审核来源与适用条件，再整理进知识或员工能力。历史运行不会自动成为团队的权威结论，也不证明下一项工作会得到同样结果。

## 首次使用常见问题 [#common-first-use-issues]

- **没有可用模型或仓库**：先检查工作区、模型目录、个人授权和连接状态；不要反复提交同一个未满足条件的任务。
- **页面读取失败**：保留当前目标与错误提示，使用页面的重新检查或重试入口；网络失败与没有数据不同。
- **结果与预期不符**：回到原输入核对范围和验收要求，在原工作上下文中补充说明，避免将相互矛盾的目标散落到多个入口。

涉及接入条件时，继续阅读[企业接入检查](/zh/docs/private-deployment)。
