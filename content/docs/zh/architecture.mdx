## 先区分不同的工作入口 [#distinguish-the-work-entry-points]

SkyBot 项目用于持续沟通目标、资料和协作工作；研发 Task 用于按流程执行一次工程目标；Automation Run 是自动化定义的一次运行。这些入口可以使用共同的执行能力，但保留各自的身份、状态和结果归属。

例如，项目里的一轮对话可以发起后台工作，但不能因为后台任务完成，就把整段项目对话判定为完成。查看进度时，应从原业务对象进入，再下钻到对应运行和检查材料。

## 控制面决定谁可以做什么 [#the-control-plane-defines-who-can-act]

Console 是用户工作台，Control Plane 负责身份与工作区授权、流程和能力版本解析、执行环境生命周期及受控派发。实际运行发生在 Sandbox 内，由 Runner 管理执行事实。

| 组成 | 负责的事情 | 不应据此推断的结果 |
| --- | --- | --- |
| Console / Control Plane | 接受操作、核对权限、解析版本、选择并管理环境 | 请求已受理不等于工作已完成 |
| Sandbox / Runner | 推进工作节点、管理尝试、Agent 会话与运行事件 | 环境就绪不等于业务成功 |
| Artifact 与检查 | 保存阶段产物、结果说明及检查证据 | 有产物不等于已人工验收 |
| Knowledge | 按当前授权检索知识并保留来源 | 检索命中不等于获得所有原文权限 |

## 研发流程如何推进 [#how-engineering-flows-advance]

Flow 描述工作节点之间的调用依赖、输入和输出。WorkNode 是可复用的执行定义；同一流程中可以调用已有发布版本，也可以包含只服务于该流程的定义。任务开始前解析适用版本和能力，避免运行中无提示地跟随外部最新版本。

一次研发工作可以组织为分析、实现、检查和交付，但这只是流程示例，并非每次工作都固定经过四步。Runner 根据真实依赖推进可执行节点，记录每次尝试和状态；下游通过声明的 Artifact 消费上游结果。

阶段交接应包含可检查的文件、结果说明和内容标识。检查失败时保留失败记录，再依据恢复策略产生新的执行尝试；不能用后来成功的结果覆盖旧证据。用户审查时应同时查看需求、变更、检查结果和交付说明。

## 知识检索保留当前权限与来源 [#knowledge-retrieval-keeps-authorization-and-sources]

Control Plane 维护知识归属、访问范围与授权，LightRAG 承担解析、索引和检索数据面。召回证据记录查询时的工作区、授权知识库、索引版本和命中引用，用来解释本次工作使用了哪些依据。

这类证据记录的是查询时的事实，不是把所有资料复制成永久可读的快照。原文访问继续受权限约束；个人记忆、项目知识和共享工具也不应混成一份无边界的上下文。

## 状态保存与问题定位 [#state-storage-and-investigation]

PostgreSQL 保存控制面结构化业务状态；Runner 的 SQLite journal 保存 Run、Attempt、事件和恢复回执；Git 保存源码事实，对象存储保存按合同管理的大对象。运行事件与 OpenTelemetry 链路帮助把用户操作、执行和模型调用关联起来。

定位失败时，先确认所属工作和运行版本，再区分环境创建失败、节点执行失败、检查失败或交付失败。停止请求受理与进程真正退出也要分开；结果未知时先查询和核对，不能假定外部操作没有发生后直接重跑。

## 隔离与部署是环境事实 [#isolation-and-deployment-depend-on-the-environment]

Task 使用隔离 Sandbox，个人开发环境则保留独立持久工作区。当前本地默认采用普通 OCI 运行时；gVisor 是需要明确配置并实际验证的另一条路线。运行时、网络规则和持久存储都必须在目标环境验收。
