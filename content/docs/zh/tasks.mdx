---
title: 创建与审阅研发任务
description: 准备需求、仓库、基线与流程，在任务中检查变更、产物和验证依据。
---

研发 Task 面向具备明确需求、代码仓库与检查要求的工程工作。它不是普通聊天记录的别名，也不以最后一句“已完成”代替代码与验证依据。

## 创建前准备 [#prepare-before-creation]

确认当前工作区、个人模型凭据、Git 连接与仓库读取权限。建议第一次选择测试仓库中的小改动，写明不能改变的行为及验收方法；这属于 POC 范围建议，不是产品限定只能处理局部修改。

选择的流程和模型还需要满足当前运行端的兼容条件。目录中看得到某个模型，并不代表你的个人凭据已配置；能查看仓库，也不自动授予合并或发布权限。

## 从任务列表创建 [#create-from-the-task-list]

进入 Tasks，选择“新建任务”，在创建抽屉里准备输入。当前界面不要求先跳去一个独立的新建工作台。

| 输入 | 含义与检查方法 |
| --- | --- |
| 任务需求 | 直接说明目标、约束和验收条件；可结合当前启用的需求来源 |
| 任务名称 | 标识本次工作，确认它准确对应需求 |
| Repository | 本次实际允许读取与修改的仓库 |
| Base branch | 作为任务基线的分支，避免误用生产发布分支 |
| 任务流程 | 选择智能编排或当前可用的已发布 Flow |
| 流程输入 | 按所选 Flow 的实际定义填写，带必填要求的项目不能遗漏 |
| 知识与连接 | 仅添加工作需要且自己有权使用的资料和工具 |

需求来源按当前部署返回的可用清单显示，可能包括 Markdown、Git Issue、知识库或外部服务；不能把界面认识某个来源等同于企业已经接通它。链接读取失败时先检查来源地址、连接和授权。

## 需求应该写到什么程度 [#write-actionable-requirements]

把验收条件写进需求正文，不假定产品有一个独立的“验收标准”字段。示例：

```text
目标：为配置保存接口补充空名称校验。
约束：保持现有权限逻辑与成功响应格式；不改动无关接口。
产物：代码变更、相关验证结果和交付摘要。
验收：空名称被拒绝，有效名称仍按原行为保存。
后续：由团队审查，不自动合并或部署。
```

如果选择工作区 Flow，输入项目来自其发布版本。仓库相关输入会与上方 Repository 对应，其余必填内容按实际说明补齐。切换流程后重新核对参数与连接，不沿用已经失效的选择。

## 创建与跟踪执行 [#create-and-track-execution]

点击创建前，检查界面是否提示模型、凭据、Git 服务、仓库、分支或流程输入未就绪。修正明确原因后再提交；读取失败不等于该资源不存在。

创建成功进入任务详情，查看本次任务的阶段与执行信息。先对应当前节点与执行尝试，再阅读会话、上下文、变更、产物和检查记录。一个节点完成，不代表全部阶段已经完成；任务创建受理，也不代表隔离环境与模型链路已经实际跑通。

## 审阅交付而不是只看摘要 [#review-delivery-beyond-the-summary]

验收时至少核对四件事：修改范围是否符合目标、变更基于哪个仓库与分支、实际运行了哪些检查、产物或交付链接能否打开。没有执行的检查应保留为未验证，不由摘要中的肯定语气补足。

代码合并、生产部署与业务验收由各自流程决定。PR 或 MR 存在时，还需检查目标分支和差异，不能把“生成了链接”解释成已经上线。

## 失败、恢复与重新建任务 [#failure-recovery-and-recreating-a-task]

等待输入时，在对应执行问题处回应。授权失败先修正连接；执行失败先保留错误与历史，再按当前详情提供的恢复入口继续，不抹掉之前的尝试。

需要改变需求基线或重建时，核对新任务的仓库、分支、资料、Flow 和必填输入，不将旧快照直接当成新的授权。重试和重建都不能自动回滚先前已发生的外部操作。

常见的“创建按钮不可用”，通常应从页面反馈的缺失凭据、无可用模型、未授权 Git 或不完整输入排查。不要用更高权限账号代替必要的授权评估。有关前置环境，见[企业接入检查](/zh/docs/private-deployment)。
