## 先分清服务配置和使用授权 [#separate-service-configuration-from-usage-authorization]

平台配置回答“企业允许连接哪些服务”，个人授权回答“当前成员可以使用哪些资源”。保存一个模型网关或连接器，不会自动为全部用户授予访问权；共享一个 Skill 或 MCP，也不会把创建者的个人密钥交给其他成员。

模型和工具的实际请求可能离开部署环境。先确认服务地址、允许发送的数据以及访问范围，再在正式设置或连接入口保存凭据。不要把 API Key、Token 或企业应用 Secret 写进任务说明、聊天示例或共享 Skill。

## 配置 LLM Gateway 与模型目录 [#configure-the-llm-gateway-and-model-catalog]

由平台 Admin 或 Operations 在平台设置的 AI Gateway 中维护 LLM 服务；当前设置提供平台预设和自定义网关入口。使用自定义网关时，填写实际 Base URL，并通过受控输入保存相应凭据。

1. 核对服务地址及网络可达性，再读取网关模型目录；也可添加企业交付中指定的模型。
2. 保留供应方返回的 Model ID，并核对模型的显示名称、支持协议和容量信息。
3. 只声明服务确实支持的协议。当前配置可表达 OpenAI Responses、OpenAI Chat Completions 和 Anthropic Messages；同一模型可能支持其中一种或多种。
4. 保存连接、凭据和模型设置后，再为对应工作入口选择兼容模型，完成一次实际调用。

目录发现成功不证明每种协议都可以使用。只有 Model ID、没有协议证据的候选，仍需确认能力；没有填写的容量或价格也不能当成已核验的模型参数。某个运行入口看不到模型时，检查入口与模型支持协议的交集，而不只看名称。

## 为知识处理单独配置 Embedding [#configure-embedding-separately-for-knowledge-processing]

Embedding Gateway 负责知识向量化，与 LLM Gateway 分开维护地址、模型和凭据。二者可以指向同一供应方，但不能假定一个连接保存后另一个也已配置。

当前 Embedding 接入支持 OpenAI 兼容的 `/v1/embeddings`。由管理员选择内置或已配置的外部服务，添加实际模型并检测向量维度，再保存默认选择。模型 ID 应按服务实际返回值保存，维度应来自真实响应。

知识索引需要相应处理链路可用。对话模型可以回复，不代表文档解析、向量化或检索已经就绪；保存后应使用一份允许导入的小文档，完成索引并检索其中明确存在的内容。

## 成员完成自己的连接与授权 [#complete-personal-connections-and-authorization]

在当前工作区的连接与授权入口，先确认账号、工作区及连接用途，再保存个人 Git / 模型凭据，或按企业连接器提示完成 OAuth。平台服务地址、个人授权状态与实际资源访问是三个独立检查点。

授权过期、已撤销或状态无法读取时，先刷新权威状态，再决定是否重新授权。不要仅因之前显示“已连接”就判断当前请求仍有效；也不要因加载失败而认定授权不存在。轮换之后使用真实请求验证，历史工作记录仍保留原来的身份与结果。

## 用一项最小工作验证配置 [#verify-with-a-minimal-piece-of-work]

选择本次确实需要的模型、工具和资料，先执行只读或有明确边界的小工作：核对模型调用，读取已授权仓库或文档，再检查工具返回的真实结果。需要外部写操作时单独说明目标与批准方式。

若模型能调用但工具失败，沿连接和资源权限排查；若知识查不到内容，沿索引与召回排查。继续阅读[知识使用指南](/zh/docs/knowledge)与[问题定位](/zh/docs/troubleshooting)。
