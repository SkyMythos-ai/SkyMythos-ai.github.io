当一次对话回合、研发 Task 或自动化 Run 结束后，不要只阅读对话末尾的一句“已完成”总结，而是应当切换到**产物、文件、变更与来源证据**视图逐项核查。

## 四类核心结果与证据视图 [#four-result-views]

| 视图分类 | 适用工作面 | 你能在这里看到什么 |
| --- | --- | --- |
| **交付产物（Artifacts）** | SkyBot / 研发 Tasks / 自动化 | 按契约输出的 Markdown 报告、`result.md`、结构化 `artifacts.json` 清单及可下载交付文件 |
| **工作空间与项目文件** | SkyBot 项目 / 个人开发机 | 项目共享目录或开发机 `/workspace` 内新增、修改的全部工作文件 |
| **代码变更（Git Diff）与门禁日志** | 研发 Tasks | 基于特定 Repository 与 Base branch 产出的代码差异、单元测试 / Lint 等 `Unit Gate` 实际运行日志与 MR/PR 链接 |
| **知识引用与链路追踪** | 所有工作面 / 可观测性 | 命中知识片段、对应发布版本号（支持点击回跳原文），以及关联的 OpenTelemetry Trace/Span 工具记录 |

## 分类型验收核查要点 [#verification-checklist-by-type]

<Tabs items={["文档与分析报告类", "代码变更与工程类", "自动化定时类"]}>
  <Tab value="文档与分析报告类">
    1. 产物文件能正常打开，排版与交付格式符合原始指令。
    2. 覆盖了全部要求维度，未遗漏关键限制条件。
    3. **逐条点开来源引用**：确认报告中的制度条款或数据结论，确实存在于对应版本原文的前后文中，而非断章取义。
  </Tab>
  <Tab value="代码变更与工程类">
    1. 核对变更基于正确的代码仓库与 `Base branch`。
    2. 逐文件审阅 Git Diff，确认未改动无关模块或引入硬编码密钥。
    3. 检查 `Unit Gate` 日志中单元测试、类型检查与构建命令是否**实际运行并通过**（凡未执行的检查项必须视为未验证）。
    4. 通过 Git 托管平台完成人工 Code Review，再决定是否合入目标分支。
  </Tab>
  <Tab value="自动化定时类">
    1. 打开单次 `Automation Run` 详情核对当次实际输入参数与步骤输出。
    2. 核查结果通知目标（如发送渠道）是否符合预期、是否存在异常重试开销。
    3. 对涉及审批或对外发信的节点，保留人工拍板后再执行后续动作。
  </Tab>
</Tabs>

<Callout type="info" title="把执行完成与业务验收分开">
  系统报告 `Completed` 或自动检查通过，说明流程已按规则执行完毕并留存了证据；最终是否达到业务标准、是否合并代码或对外发布，始终由责任人基于上述真实证据做出判断。
</Callout>

如果准备好亲自跑一遍完整闭环，请继续阅读下一篇[开启你的第一个任务](/zh/docs/getting-started)。
