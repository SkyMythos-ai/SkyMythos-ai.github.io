**研发任务（Tasks）** 面向需求明确、涉及代码仓库并要求确定性检查的工程交付工作。与自由对话不同，Task 在创建时即冻结输入规格（`TaskSpec`），在独立隔离沙箱中按阶段推进，并以可审查的代码变更和检查证据作为交付标准。

## 创建前的就绪检查 [#prepare-before-creation]

发起研发任务前，请先确认以下四项条件已经满足：

1. 当前工作空间内已配置兼容该执行入口的模型服务目录，且你已拥有可用的个人模型凭据或平台授权。
2. 已绑定个人 Git 凭据（`User Git Credential`），且对目标 `Repository` 具备读取权（注意：能读取仓库不代表自动授予向受保护分支合并代码的权限）。
3. 选定了安全合理的 `Base branch`（基线分支），避免误选直接触发线上发布的生产分支。
4. 若选用自定义已发布 Flow，已备齐该流程定义中标记为必填的流程输入参数与关联连接。

## 创建研发任务与填写规范 [#create-from-the-task-list]

进入一级导航 **研发任务 → 任务列表**（`tasks`），点击“新建任务”打开创建抽屉。表单包含以下核心输入：

| 字段 | 作用与核对重点 |
| --- | --- |
| 任务需求（Requirements） | 写清业务目标、架构约束与验收条件；可从 Markdown、Git Issue、知识库等当前启用的来源导入 |
| 任务名称（Task Name） | 准确概括本次工程改动目的，便于团队检索与审计 |
| Repository | 本次任务允许读取和产生代码变更的目标仓库 |
| Base branch | 创建任务分支的基线分支 |
| 任务流程（Flow） | 选择“智能动态编排”或工作空间/市场中已发布的标准 Flow 模板 |
| 流程输入（Flow Inputs） | 依据所选 Flow 定义动态展开；带必填标记的字段不可遗漏，切换 Flow 后需重新核对 |
| 知识与连接（Knowledge & Connections） | 仅勾选本次任务确实需要且自己有权访问的知识库与工具连接 |

### 如何编写高质量的工程需求 [#write-actionable-requirements]

建议将**验收条件与禁止越界范围**直接写进需求正文（不要假定存在某个隐藏的“自动验收开关”）。示例模板：

```text
目标：为配置保存接口补充空名称校验，并返回标准 400 错误码与字段提示。
约束：保持现有权限校验逻辑与正常保存的响应格式不变；不重构无关模块。
产物：代码变更 Diff、对应单元测试结果（Unit Gate）与交付摘要。
验收：空名称或纯空白名称被拒绝；有效名称保存与既有单测全部通过。
后续：仅生成变更与交付说明供人工 Code Review，不自动合并主干或触发部署。
```

<Callout type="info" title="需求来源可用性提示">
  创建抽屉中展示的需求来源类型取决于当前部署配置；若导入外部链接失败，请先核对来源地址、个人连接状态与授权范围。
</Callout>

## 跟踪阶段执行与审阅交付证据 [#track-execution-and-review-delivery]

点击提交前，界面会自动检查模型、Git 凭据、仓库、分支与必填参数是否齐备；若创建按钮不可用，请根据页面反馈逐项补齐，不要使用管理员高权限账号绕过普通成员的授权检查。

创建成功后进入任务详情页，按以下顺序审阅过程与成果：

<Steps>
  <Step>
    ### 核对当前节点与执行世代

    先确认任务处于哪个 WorkNode 节点以及对应的 Execution Generation / Attempt 次数。单个上游节点完成不代表整个 Flow 已经交付。
  </Step>
  <Step>
    ### 查看实时会话与工具记录

    展开当前节点的 Agent Session 输出与工具调用记录，了解 Agent 如何理解需求、定位文件与执行测试命令。
  </Step>
  <Step>
    ### 核验代码 Diff、Artifact 与门禁结果

    验收交付物时至少核对四项事实：① 代码改动范围是否严守约束；② Diff 是否基于正确的仓库与基线分支；③ 确定性检查（Unit Gate / 单测 / Lint）是否实际运行并通过（未执行的检查应诚实标记为未验证）；④ 生成的产物文件与摘要链接是否可正常打开。
  </Step>
  <Step>
    ### 人工 Code Review 与合并上线

    当产物包含 PR/MR 链接时，请回到 Git 托管平台检查目标分支与完整差异，由仓库负责人按团队规范合并并触发后续 CI/CD 发布。
  </Step>
</Steps>

## 等待介入、失败恢复与重构任务 [#failure-recovery-and-recreating-a-task]

- **等待人工输入或审批**：任务暂停等待回应时，直接在对应节点的问题卡片处回复确认或补充说明。
- **门禁失败或定向返工（Fusion Resume）**：授权过期请先修复连接；若因代码问题或检查未通过而失败，保留历史失败尝试记录，利用任务详情页提供的恢复入口从指定 WorkNode 发起新一次尝试或补充返工指令。
- **需要更换基线或重设范围**：如果需求目标或基线分支发生根本变化，应新建任务并重新核对仓库、分支、资料与 Flow 参数；重试与重建都不会自动回滚此前已经发生的外部操作。

如需了解如何从零编排自定义研发流程与质量门禁，请继续阅读[研发流程（Flows）与工作节点编排](/zh/docs/flows-worknodes)。
