# AgentTeams：让图解释关系，而不是给文字加边框

## 触发与范围

2026-10-20 用户指出最新官网「全部都一团文字挤在一起」，建议参考阿里云 AgentTeams。当前官网的[工作、资产与治理内容合同](work-assets-governance-outline.md)解决了信息覆盖，但其静态首屏、资产说明和治理条目仍主要依赖阅读；信息完整不等于视觉表达有效。

本次通过浏览器访问并实际查看官方产品页首屏、整页、产品总览图和企业数字员工场景图，也查看了官方产品概述文档渲染页。另有官方文档文本核查，用于辨别版本与承诺范围。只使用公开页面，没有登录控制台、运行产品、复现业务或观看完整发布会视频；不声称核验全部交互、手机布局或实际产品效果。本轮仅研究，未修改官网组件。

## 1. 产品方向为何可比较

官方产品页定位为企业多智能体治理与协作平台，主标题「让 Agent 开始团队协作」。产品介绍将统一治理、协作编排、安全合规、成本可控放在一起；场景涵盖企业数字员工、Team 服务化、SaaS Team 赋能、存量 Agent 纳管。[来源：官方产品页](https://www.aliyun.com/product/agentteams)

这与我们的工作组织、企业资产复用和治理问题域相近，但不证明双方实现相同。官网只借鉴讲解对象与关系的方法，不照搬其 Matrix、WAT、独立计费、安全或限额告警等承诺。

## 2. 已实际观察到的视觉组织

| 页面位置 | 实际呈现 | 可借鉴之处 |
| --- | --- | --- |
| 首屏 | 产品类别与一句主张、两个操作入口，右侧品牌图形；没有把全部能力展开 | 第一眼只承担定位，不先讲完整工作步骤和治理算法 |
| 产品介绍 | 两段介绍下面是一张宽幅总览图 | 系统关系由图承担，正文不反复描述图中所有模块 |
| 总览图 | 上方用户入口；中心 Worker 团队含 Team Leader、Worker A/B 与连接；左侧 Worker／AI 资产；右侧 Human、LLM、MCP；下方观测／评估／调优 | 区分谁做事、调用什么、留下什么、谁介入；连接线表达关系，不能仅把名词排成卡片 |
| 产品优势 | 四个相对短的价值块，位于大图之后 | 读者先理解对象，再用短语总结，不用优势清单代替产品说明 |
| 典型场景 | 横向场景展示，图在上、场景名与短说明在下，场景下有短价值标注 | 每张图围绕一个使用情境，改变角色与资源关系，不是同一架构图换标题 |
| 安全合规 | 四项主题配图与短说明，细节不全部塞入总览 | 专题解释与主要流程分层；不必照搬其装饰性图片 |

实际观察还包括：官方页并不是完全无文字，也有卡片和较长介绍；可借鉴的是「大图为主、文字作总结、场景分别讲」，不是无条件复制它的全部布局、渐变、横向轮播或白色主题。

## 3. 当时页面的问题与研究建议（历史）

| 当前问题 | 建议画面 | 要删减或下沉的内容 |
| --- | --- | --- |
| 首屏把工作／资产拆成文字面板，仍需逐句阅读 | 一张具体产品关系主图：人提出目标，SkyBot 与专业员工组织工作；工具和模型作为执行能力，资产作为经授权复用对象，治理贯穿 | 删除主图里的长标题解释与重复标语，首屏只留固定产品定位和一句价值 |
| 资产章用三个来源框和一段结果文字，缺少可辨认的资产与实际引用 | 同一案例的产物与经验，经人确认后形成具体可复用方法，再被下一项任务引用；用来源、版本、共享范围作少量标签 | 「有来源／有维护／有边界」三段说明改为图中对应位置的短标注 |
| 治理章左侧三句大字、右侧三组段落，本质上整屏是文字 | 以一条真实结构的运行记录为主体，展示成员、模型、Token／估算费用的归属，再连接模型策略与新 Task 准入点 | 删除两侧同义标语；长权限矩阵、UTC 规则、并发与遥测说明下沉文档；首页保留不可省的估算／入口范围限定 |
| 架构页过度依赖大表和长定义 | 总图保留组成与责任边界，局部机制图只说明计量与准入，不再重复首页价值图 | 降低连续定义条目密度，具体操作仍由文档承担 |

以上为研究阶段的历史建议，后续经历独立草稿、深石墨正式接入，再由产品画面优先的新设计取代。当前实现以[内容合同](work-assets-governance-outline.md)为准；工作→资产→治理的阅读顺序、确认角色与播放约定保留，深石墨主题及首屏协作图不再是当前视觉要求。

### 图稿必须通过的检查

- 不读解释段落，能指出主体、动作、输入与输出；关系图能说明连线的含义。
- 同一案例贯穿工作和复用，不为每屏更换一套抽象例子。
- 每屏先有一张主要画面，再配一个标题、一句解释和少量标注；把段落拆成更多卡片不算减负。
- 图示与真实产品截图明确区分。没有真实可用数据时标记「示意」，不伪造客户费用、使用率或节省比例；用具体对象示例也不意味着已经在生产发布。
- 桌面和手机先看静态图稿，再接自动播放；保持 hover 不暂停、键盘及减少动态边界。
- 详细能力限制留在对应架构／文档，但不能删掉会改变购买判断的范围：估算不是账单，Task 准入不是全入口硬预算，管理员没有无限私人内容读取权。

## 4. 文档与版本边界

- 当前 AgentTeams URL 下的[快速入门](https://help.aliyun.com/zh/agentteams/magic-quick-start)正文使用 AgentCore，页面更新时间为 2026-10-13；不能仅凭路径把全部当前内容视为旧产品能力。
- [迁移说明](https://help.aliyun.com/zh/agentteams/agentteams-has-been-migrated-to-agentcore)描述 AT 实例控制面资源迁往新的 AC Workspace，不包含全部运行时记忆、任务产物、历史会话与用量，迁移不是无损更名；页面日期不是产品切换生效日。
- 官方营销页提及成本计量和限额告警，[费用页](https://help.aliyun.com/zh/agentteams/billings-of-agentteams)另有公测免费及依赖资源独立计费说明。它们不能直接合成为现行合同价格，也不作为我方告警或硬预算已实现的证据。
- 文档入口用于配置与操作，不应复制其帮助中心的正文密度到营销首页。有关我方能力仍以[已有代码证据矩阵](work-assets-governance-outline.md)为准。

## 下一步

2026-10-20 已按上述方向产出三张独立静态网页草稿，包含桌面／手机分别编排的产品总览、资产复用、使用治理示意。用户评价「效果还行」，同时明确要求使用 `design-taste-frontend` 重新调整动画。这是继续动态设计的反馈，不是正式页面或上线验收。

随后在独立本地预览中重编三段动画：目标经协作形成交付并回到人；工作记录经人确认形成方法，后续任务再授权复用；已记录运行关联消耗，再对新的 Task 检查准入。治理允许／拒绝分轮展示，传输路径与数据卡同步出现，不倒放业务因果。用户进一步提出动画应当叠加、不能过去后就消失，已据此将「稳定结构／已形成结果／当前任务」分层：交付逐项叠加产物、依据和确认；来源、Skill、版本与复用标记跨轮保留，新任务取得引用；运行与消耗记录不随新准入情境清空。后续只切换任务状态，不重新演示形成资产或记账。保留已确认角色、石墨主题和既有正式 URL，不添加真实费用数字或假控制台。

用户随后要求整体优化官网，并批准将累积式动画接入正式源码，先形成深石墨版本：首屏紧凑协作图、资产复用与治理图，工作章节为真实交付截图。该版本及原型属于历史视觉基线，不能作为当前浅色版验收。

之后用户明确要求抛弃之前风格，已批准并实施产品画面优先的新设计：真实交付首屏、全宽执行案例、培养截图与资产复用图、治理机制及开放接入关系；营销近白／深墨／品牌蓝并跟随系统浅深主题，文档固定浅色。旧 overview 不再挂载首页；资产、治理与完整培养图重排，继续使用已验证的累积模型和播放合同。正式实现不依赖草稿目录、iframe 或生成器；当前内容以[内容合同](work-assets-governance-outline.md)为准，实际验证及性能缺口见[任务 Review](../tasks/todo.md)。未提交、推送或部署，不沿用原型 Lighthouse 分数代替正式页面验收。
