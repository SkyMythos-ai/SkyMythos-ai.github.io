# 设计经验

## 同一首屏分幕讲故事，不用长对白补流程

- 用户认为专项员工长片文字过多，先要求拆片，随后明确三幕都应留在首页首屏，以动画和自动轮播串起完整故事；下方三个独立短片仅保留为历史对照。
- 当前候选规则：左侧主张固定，右侧同一舞台按完成工作、能力留下、复用改进推进；每幕一个主要价值、一句标题，以人物、物件交接和成果变化承担解释。不回到长对白、过程字幕和版本说明，也不把三块互不相关的功能面板称为故事。
- 边界：首轮形成过程与后续查看轮播分开；轮播只转移关注，员工身份、原方法、来源和旧成果保持，不重复制造人的确认。手机自然纵向展开，不强行压进一屏。
- 验证：实际观看首轮和至少两次完整关注轮播；检查手机可读性、角色与方法显隐、无 JS 和减少动态完整结果。无播放／阶段按钮，hover 继续，键盘／离屏／后台冻结。候选与正式迁移分开验收，不能拿草稿成绩代替中英正式组件与全站验证。

## 专项数字员工与学习要通过身份和行为变化表达

- 用户认可微缩立体与二维角色风格后指出：只有方法归档和纸页引用，仍看不到专项数字员工，以及经验在 Agent 中复用、学习和进化。
- 规则：专项员工应有持续且区别于通用协作 Agent 的身份、明确职责和实际使用的方法／工具；能力就绪后再委派，不能给原 Agent 换个名字或加升级标记就算形成专业员工。沿用已确认角色，不靠新机械外形表达专业性。
- 最新职责规则：AI 主动推进学习、总结，提出经验、方法与改进候选；人审核、二次修改、确认并决定采用，不由人替 AI 筛选或编写总结。两轮都须显示一处真实内容修改，不能用确认章代替审核修改；确认和采用先于生效与后续任务复用。
- 规则：用具体反馈串起 AI 候选经验、人的审核修改确认采用、方法修订与下一任务引用，让改进体现在执行顺序或成果差异里。企业方法、员工经验、固定角色版本和历史任务分别维护；不把经验整理画成模型自动训练、全员同步升级或保证效果提升。
- 验证：能追踪同一位员工、方法原件、引用与修订；原成果和旧版仍在，新任务实际采用改进方法，旧任务不被反向改写。手机需要放大或重排关键差异，不能只塞进更多小字。候选优化与正式页面合同分开记录。

## 视觉风格和动效编排是两个维度

- 用户纠正：连续镜头、纸页动作和透视模块如果仍使用同一套工作台、卡片、颜色与构图，只是同一风格的不同布局／动作，不能作为「完全不同设计风格」让用户选择。
- 规则：风格候选必须改变主视觉的构成语言、材质、字形重量与角色：例如平面编辑图形、实体微缩场景、二维角色叙事。只固定产品主张与故事，不固定同一套界面外壳。先交付静态构图，确认差异成立后再做动画；不要用镜头运动掩盖缺少视觉差异。
- 验证：暂停、去掉风格标题后，仍能区分三套设计；立体场景必须是有体积的物件，不是倾斜的网页。旧动效实验保留作参考，不再作为当前风格候选。静态稿明确未接入动画，不把它描述为可播放成品。

## 用同一份工作的因果串起故事，而非轮播功能面板

- 用户认可工作空间草稿的视觉感觉后，强调核心仍是「用一个故事小动画串起来」。
- 规则：固定人物、目标与成果对象，让审阅和修订改变成果，人的确认先于方法保留；下一项工作的起点必须直观体现前一次留下的方法。方法提取、保留和引用沿用同一身份、文字和外观，避免把几个不相关面板依次出现称为故事。
- 用户进一步要求同一项需求的完整生命周期：固定需求身份，让范围确认、方案、实现、验证、发布、反馈和下一版有明确因果；不把多个 Agent 岗位轮流亮起当成生命周期，也不把下一版换成无关新任务。已发布快照和旧方法引用不反写，改进版仍须保留人的验收／发布关口。
- 验证：原方法不因引用而从企业库消失，原成果不因新任务而清空；展示引用副本而不是把原件搬走。等待确认、已确认正在保留和保留完成的提示必须与时间线一致。故事草稿与正式页面分开验收。

## 占满首屏不等于撑高容器，动效不等于移动数据点

- 用户否定整屏开放图的观感：空白仍过多、右侧动画平庸，要求重新考虑设计。
- 规则：视口高度增长时，主视觉的面积、层次和视觉重量也要增长，不能把小对象垂直居中后称为整屏。先做独立可播放草稿，验证成果展开、确认、方法保留和再次使用的形态变化，不再靠细连线和移动小方块承担整段宣传，也不默认用粒子／霓虹／漂浮填空。
- 边界：用户确认草稿方向前不替换正式首页；保留浅色、角色与因果，不把草稿的视觉认可等同于正式产品或性能验收。

## 首屏是完整价值场景，细节在下方证明

- 用户进一步要求：首页第一屏占满，左侧文字主题、右侧动画体现核心价值，下方再分点介绍，而不是结构卡和案例直接上下堆叠。
- 规则：桌面先建立独立首屏，使用导航下剩余视口作为最小高度、专用宽版心与开放场景；通过成果交接表现工作、人工确认和能力复用，不给旧功能框加头像就称为场景。下方按工作、资产与治理逐项证明，不重复首屏完整故事。
- 验证：宽屏下一节不提前挤入，短屏 CTA 可达、完整场景不裁切，手机自然展开；路径按对象实际位置随双语换行和响应式重排更新，数据片不能越出场景。占满不等于所有设备都强制固定一屏。新增标题、CLI 注记或图注时，重新计算整个右栏的高度预算，不能只给 SVG 设 max-height 后仅验证 CTA。检查短桌面视口及单双栏断点两侧，避免 1024 桌面过早堆叠；具体断点以当前候选与用例为准。

## 局部案例不能代替平台定义

- 用户纠正：首页首屏只集中展示订单研发执行，遗漏整个平台的核心价值；明确认可「让 AI 完成工作，让能力留在企业」作为宣传重心。
- 规则：首屏保留模型、Agent、知识和工具组成企业工作体系的定义，不以局部研发状态机代替平台价值。原生订单执行面板下移为案例；2026-10-22 用户确认的虚构需求生命周期可作为首屏叙事，但必须说明示意边界，下方仍分别证明工作、资产与治理，不能因为新故事而删除治理或改变平台定位。
- 验证：不读订单案例也能说清平台价值；图中人的整理确认、复用回路和治理贯穿可辨，对话、研发任务与自动化是可选入口。原生案例本身通过测试，不等于其首屏定位正确；内容合同见[工作、资产与治理](../research/work-assets-governance-outline.md)。

## 产品画面可以原生重建，但不能冒充真实运行

- 用户希望截图用原生界面实现，保留贴图般的产品质感，同时让内部过程生动起来；先从首屏执行计划做起。
- 规则：让任务状态、进度、记录、检查和交付推进，而不是让整张图片漂浮或放大。完成状态与结果保留，查看循环不重新制造执行或人的验收；手机原生排版，不缩小整张桌面截图。
- 边界：重建画面明确标注「界面演示 · 示例数据」，保留未经修改的真实原图入口；不借演示扩大产品能力或制造业绩证据。沿用无控制按钮、hover 继续、键盘／离屏／后台暂停及减少动态回退。
- 验证：运行中切换减少动态不仅应停时钟，还须显示完整静态结果；帧内也检查偏好，不能只依赖媒体查询 change 事件。动态提示应为所有文案共同预留布局，避免英文在平板换行时撑高画面；检查全部响应式宽度的时间点，不只看桌面和手机。实际检查原生布局、过程与结果留存、弹窗及恢复，不以纯模型或静态截图代替播放验收。

## 参考风格要统一底层系统，不靠追加覆盖修补

- 用户纠正：提供 Coworker 产品场景页后，明确「深色不搭」，新版仍像「贴膏药」。
- 规则：先确定整页背景、字重、按钮、圆角和版心，再明确每个活动组件的唯一样式归属；移除已被替代的全局导入，而不是继续叠高优先级。当前全站固定浅色，取代上一轮系统浅深主题，不沿用旧设计偏好抵消最新反馈。
- 验证：用真实浏览器审阅完整页面及跨页外壳；系统 light／dark 下均固定浅色，双语桌面与手机的标题、按钮、媒体和页脚同源。参考站只提供视觉关系，不提供本产品的品牌、能力或业绩证据。当前约定见[内容与视觉合同](../research/work-assets-governance-outline.md)。

## 明确要求抛弃风格时，重做构图而不是旧图换色

- 用户纠正：先前整站优化后仍要求「抛弃之前的方案，重新全部设计」。
- 规则：撤销上一轮的视觉约束，重新决定主题、主要画面、页面构图和阅读节奏；已经确认的产品事实、角色、链接、动画因果与可访问性行为不随风格重做丢弃。真实产品画面、机制图和短文各承担不同职责，不把所有章节重新画成同一种左右分栏。
- 验证：用实际构建的桌面／手机画面比较主视觉、章节构图及图形载体；颜色变化、类型通过或自动化数量不能单独证明完成了重设计。当前设计以[内容与视觉合同](../research/work-assets-governance-outline.md)为准。

## 动作结束，结果留下；新动作建立在已有结果上

- 用户纠正：有些动画应该叠加，不应该过去后就没了。
- 规则：分开稳定结构、已形成结果、当前任务状态与短暂传输。产物、检查依据、人的确认逐项叠加；记录、确认和 Skill 形成后保留，后续任务取得引用，不搬走原资产。运行与消耗记录也不因切换准入结果被清空。后续循环在已有结果上演示新工作，不反复从无到有创建相同资产。
- 边界：传输线仍只在实际示意交接时出现；结果保留不等于让所有线路常亮，也不等于同一个请求同时允许和拒绝。任务切换只重置本轮状态，不让稳定角色、来源、企业资产和既有运行记录一起淡出。
- 验证：检查首次形成之前、结果叠加中间帧，以及循环边界前后。保留对象的透明度不下降、位置不跳变；跨至少三轮验证来源和资产仍在，后续不重播形成／记账，任务决策互斥。

## 信息完整不能靠堆文字，图必须承担解释

- 用户纠正：加入资产和治理后，官网仍然「一团文字挤在一起」，应参考阿里云 AgentTeams 的产品表达。
- 规则：不能把段落换成文字卡片就称为图形化。先画出具体主体、动作、资源、产物与关系；场景用同一案例解释，文字只留标题、短说明和必要标签。资产与治理也要有主要画面，而不是一侧标语、一侧长列表。
- 验证：不读解释段落仍能辨认谁做事、使用什么、留下什么、怎样管理；先看桌面／手机静态图稿再接动画。参考[AgentTeams 图形叙事研究](../research/agentteams-content-reference.md)，不复制对方品牌、图像或未核验的功能承诺。

## 工作、企业资产与治理共同构成产品价值

- 用户纠正：官网不仅要讲一次工作的完成，还须体现企业 AI 资产沉淀、员工 AI 使用管理与成本治理；先讨论信息归属和层次，再改布局。
- 规则：产品首页以工作、资产、治理递进表达价值，工作方式解释过程，架构解释组成与边界，文档承接操作。治理贯穿系统而非业务最后一步；不按员工／管理者割裂营销叙事，文档可以按实际职责和任务导航。
- 验证：核对使用可见范围、费用计量来源、控制生效入口和共享资产权限。区分代码支持、部分支持、待核验；没有证据不等于产品规划，配置预算不等于硬阻断，消耗不等于员工绩效。目标大纲见[工作、资产与治理](../research/work-assets-governance-outline.md)。

## 背景连续，避免用实色色块拼接层次

- 用户纠正：背景不够通透，像单纯的色块拼接，缺少细腻层次。
- 规则：多个章节共享连续底色，以留白和内容关系区分层级，减轻重复套框及页脚实色块；菜单可读性优先。不把「通透」等同于玻璃化、蓝紫光晕或额外动画。石墨与柔光是当时方案，不是永久规则，已被后续产品画面优先的新视觉取代。
- 验证：同尺寸、同内容和同静态阶段做前后对比；检查手机、文字对比、减少透明度回退及浅色文档隔离。以实际构建 CSS 检查滤镜是否生效，不能只看源码；自动化通过不代表用户已经认可视觉效果。

## 先分清页面职责，再调整动画与排版

- 用户纠正：产品、概念和架构仍混乱，应参考产品 Keynote 重组官网，而不是继续局部修饰。
- 规则：首页回答产品是什么与为什么需要，工作方式页沿同一案例解释如何完成与复用，架构页先给全貌再说明边界，文档承接配置与诊断。每段主要内容有唯一归属，不能用不同图形在多页重讲员工培养。首屏产品定义固定，动画支持同一个主张。
- 边界：对话协作、研发 Task 与 Automation Run 是不同工作方式，不能用一条研发状态机代表全部产品。完整培养过程仍须先记录经验、后人确认与员工形成；已有员工参与工作的概览与培养图分开说明。
- 验证：逐页检查它回答的读者问题及重复内容，使用同一个业务示例贯穿过程；导航、元数据、链接、手机与真实跨页导航一起验收。当前分工见[工作、资产与治理内容合同](../research/work-assets-governance-outline.md)；[Keynote 官网页面职责](../research/keynote-website-information-architecture.md)保留历史来源。

## 人与 Agent 先做简洁形象草稿，再接入动画

- 用户纠正：机械人物改成圆润立体造型后仍显诡异；需要简单化，先设计人和 Agent 的形象图片草稿，不能继续直接修改网页动画。
- 规则：亲和不等于增加写实五官、肤质渐变或胶囊关节。先以独立静态稿比较简洁轮廓、比例和辨识度；人保留人的特征，Agent 不必强行拥有人的身体。去掉不必要的肢体、关节、立体材质和装饰，不在尚未认可的形象上继续叠加动作与场景。设计方向确认后再接入已有工作流程。
- 用户进一步纠正：明确要求照原版使用 Grok Bot 时，不要继续改成自己的近似造型，也不要把直接复用的要求替换成“借鉴后原创”。优先核对并使用原始视觉数据，保留用户已选定的其他部分；原站不可访问时说明所用存档来源与核验限制，不把第三方改稿当成官方原版。
- 验证：先看独立大图与实际缩小尺寸，比较人和 Agent 是否清楚、协调且不怪异；图片草稿与已确认方案分开记录。确认后再检查动作、交接与遮挡，类型、构建和几何检查不能替代用户对形象方向的认可。

## 流转轨迹只在实际传输时出现

- 用户纠正：记录归集、经验用于培养员工的轨迹不应一直存在；没有数据流转时不显示线路。
- 规则：表达动作的轨迹与对应数据卡片共用同一模型的显隐状态，流转开始时出现，结束后淡出；不能当背景装饰常驻，也不另设可能漂移的计时器。结构关系线与传输轨迹区别处理，不一刀切隐藏所有线。
- 验证：逐帧比较轨迹与数据卡的透明度；开场、整理确认、形成后及循环回起点均无残留。桌面／手机两条路径及减少动态、无脚本回退都需要检查。

## 不把受众标签直接做成页面结构

- 用户纠正：不要直接展示「员工视角／管理者视角」或轮播两篇受众说明。应通过一条流程，把双方关心的事自然结合，让价值从实际工作中被感受到。
- 规则：从日常工作及其记录、经验出发，经人整理确认后形成数字员工，再承接下一项任务并由人审阅。个人减负、团队方法积累、过程透明与交付质量嵌入这些节点，不另列管理者／员工卡片或切换入口。图中流转必须实际发生，不能只换文案，也不能直接以就绪员工开场、事后补回经验。

- 规则：技能中的圆角、嵌套外壳、导航和动效是可评估的技法，不作为整站换样式的目标。先保留已有视觉成果，只针对明确不足做小范围改善；风格变化必须先与原版同视口对比，不凭规范检查通过判断设计更好。
- 验证：比较首屏主体、整页节奏与手机阅读；当用户明确认为退步，先恢复已验证基线，再讨论后续具体改善。
- 用户进一步明确：产品为 ToB 的 AI Native / AI Infra，需重点思考每个主题的动画，现代、科技、数字、简约、时尚，可使用多色彩。后续先设计主题主体与动作，以克制的多色和材质表达工作机制，不将消费产品的圆角面板风格套在整站上。
- 用户认可三幕主体与动作，但指出色彩样式偏卡通，并给出 APIGO 开源站参考。规则：多色彩不等于大面积糖果色；避免把证据、方法和索引做成厚积木，用中性色承载主体、少量色彩标记工作，减少厚侧边、弹跳和高亮塑料感。验证：对照上一版静态与完整播放，同时检查色彩占比、材质、边缘和动作，而不是只降低饱和度。

## 域名解析正确与 HTTPS 就绪必须分别验证

- 用户反馈：按 DNS 与 GitHub 自定义域名步骤设置后仍无法访问。
- 规则：不能仅凭 DNS 记录正确推断站点可用；分别检查公共解析、GitHub 域名健康状态、实际响应服务器与 TLS 证书。普通请求仍命中旧服务时，使用指定正确边缘地址的请求区分本地或代理缓存与托管服务的问题；不把强制地址检查成功表述为普通用户访问已恢复。
- 验证：HTTPS 请求必须启用严格证书校验并返回真实页面，HTTP 必须正确跳转；证书仍处于申请状态时明确报告未完成。按官方建议重启证书申请后保持域名和 DNS 稳定，避免重复重启延长等待。
